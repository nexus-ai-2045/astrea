## 最終ゴール

**「話してよかった」と思える占い体験を、自分の手元で完結して提供できる状態。**

分解するとこの4つ。

1. **鑑定として成立している** — 実計算された命式とカードを根拠に、相談者の言葉を拾い、
   気づきを返して、前向きに締める。占いを盲信させない
2. **待たされない** — 応答が会話のテンポを壊さない
3. **続きがある** — 2回目に来たとき、前回を覚えている
4. **人に見せられる** — 結果を共有でき、名義もプライバシーも安全

---

## MVP の定義（ここが最優先。他は全部あと）

**1回の鑑定が、最初から最後まで、一度も詰まらずに通ること。**

具体的にはこの一連が完走すること。

```
出迎え
  → 生年月日を伝える
  → 命式が算出される（西洋占星術 / 数秘術）
  → タロット3枚が伏せて出る
  → 自分で3枚ともめくる
  → 数往復の対話
  → 本鑑定（🌟星盤 / 🔮カード / ⭐三つの道 / 🌙一言）が出る
  → 会話が DB に残る
```

### MVP の完了条件

| # | 条件 | 状態 |
|---|---|---|
| M1 | 出迎えが出る | ✅ 2026-08-07 |
| M2 | 生年月日から命式が出る | ✅ 牡牛座を算出 |
| M3 | カード3枚が伏せて出る | ✅ 展開法の選択を挟む形に変更 |
| M4 | **タップした札だけが開く** | ✅ |
| M5 | **3枚めくると次へ進む** | ✅ |
| M6 | 対話が数往復できる | ✅ 入力欄の復帰も確認 |
| M7 | **本鑑定（4見出し）が出る** | ✅ **初到達** |
| M8 | 会話が DB に残る | ✅ 6件 / 本鑑定 760字が完全保存 |

**MVP 完走（2026-08-07）。実 `claude -p` でも通し確認済み。**

bridge なしの本番構成で、出迎え 0.1s（LLM 不使用）→ 命式 6.3s →
展開法+札 6.9s → 本鑑定 16.5s。本鑑定の 4 見出しがすべて出た。
モデルは展開法を 3 つ名前で提示し、位置（状況/障害/助言）を守って読んだ。

検証の要点として、画面のラベルと鑑定プロンプトの位置が一致することを実機で
突き合わせた。真ん中→右→左 の順にタップして、画面 `状況=女帝 / 障害=恋人 /
助言=運命の輪`、プロンプト `1枚目【状況】女帝 / 2枚目【障害】恋人 /
3枚目【助言】運命の輪`。ここが割れると「障害」と表示した札を鑑定が「助言」と
して読む事故になるので、テストと実機の両方で固定してある。

## Phase 1 — 鑑定の質

MVP が通ってから着手する。**ここが前版に無かった軸。**

### 1-1. タロットのスプレッド定義（未定義）

いま3枚めくるが、**その3枚が何を意味するか決まっていない**。
`src/lib/tarot.ts` は「1枚目/2枚目/3枚目」としか言わない。

決めること: 過去/現在/未来か、状況/障害/助言か、別の何か。
めくった順に意味が割り当たるので、「どれを選ぶか」に意味が生まれる設計にする。

### 1-2. 対話プロンプトの設計見直し

現状はサーバが**いまどのフェーズかを一切把握していない**。
フェーズ1〜5の進行はすべて system prompt 内の指示任せ。
そのため「生年月日を聞く前に本鑑定に飛ぶ」等が起きても検知できない。

検討: フェーズをサーバ側の状態として持ち、遷移を制御する（= エージェント化）。
MVP が通って初めて、どこが破綻するか分かる。**通してから設計する。**

### 1-3. 鑑定の質の測り方

`src/lib/session-scorer.ts` があるが基準が曖昧。何をもって良い鑑定とするかを定義する。

### なぜ前版で進まなかったか（記録）

前版は Phase 1 に性能改善を置き、その前提として大量の基盤作業（セキュリティ、
`claude -p` 移行、bridge、E2E 設計）を積んだ。どれも必要だったが、
**本鑑定に一度も到達しないまま**進んだため、成果が体感されなかった。
タロットのめくりが本鑑定への唯一の通り道で、そこに3種類のバグが順に出て毎回止まっていた。

教訓: **通り道を最初に通す。** 周辺を固めるのはその後。
